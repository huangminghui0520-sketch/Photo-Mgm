## 0. 一句话结论

**现有弹窗功能已经齐全，真正的设计问题是「单击」这一个动作被塞了两个含义。** 需要你从三个模型里选一个，其余细节我按选定模型推导。

## 1. 现状盘点

### 1.1 弹窗已经有什么

读代码确认，`EventPhotosSheet` 已达成的能力：

| 能力 | 现状 |
|---|---|
| 标题栏 | 事件名 + N 张、已选 N、清空、关闭 |
| 操作栏 | 批量移动、移除、台账标记（选中 1 张时可用） |
| 网格 | 3 列，高度自适应（少时包裹、多时封顶 80% 屏高并滚动） |
| 单元格状态 | 选中=3dp 主色边框 + 35% 黑遮罩 + 右上对勾；台账槽位角标（1 主色 / 2 琥珀） |
| 移动目标 | 带搜索的选事件弹窗 |
| 移除 | 二次确认，仅回未匹配池、不删源文件 |
| 放大 | 双击全屏大图 |
| 台账恢复 | 「照片1/照片2 恢复默认」 |

**所以这一轮不是从零设计，是解决现有交互里的具体缺陷 + 补齐缺口。**

### 1.2 三个真实缺陷

#### 缺陷①（核心）「单击」含义冲突

现有实现（[PreviewScreen.kt:935-962](../app/src/main/java/com/photomgm/app/ui/PreviewScreen.kt#L935-L962)）用**300ms 手动双击检测**：

```kotlin
if (now - lastTapAt < 300) {
    onToggle()   // 回滚第一次单击的选中切换
    onZoom()     // 双击 → 放大
} else {
    onToggle()   // 单击 → 选中/取消
}
```

代码注释自己写着「回滚第一次单击的 toggle（净不变）」。这带来三个后果：

1. **视觉抖动**：想放大一张照片，会先看到它被选中、再被取消，然后才放大。
2. **无法区分意图**：用户第一次点按的瞬间，系统不知道他要"选中"还是"放大"，只能猜。
3. **300ms 的代价**：想把这张**取消选中**，也可能被误判成双击而弹出大图。

#### 缺陷② 放大视图能力过弱

现在的"放大"是**单张静态大图**，没有：

- 左右滑动看下一张（核对时最需要——「这批照片是不是同一个事件的」必须连着看）
- 双指缩放（看桩号牌、路面细节要靠缩放）
- 当前是第几张 / 共几张
- 拍摄时间、GPS、文件名等信息

#### 缺陷③ 信息不足，靠猜判断归属

核对时用户要回答的是「**这张照片是不是这个事件的**」。现在弹窗里只有图片本身，没有：

- 拍摄时间（与事件的 09:12～09:26 对照）
- 拍摄地点（与事件的 K123+000 对照）
- GPS 与事件群组是否一致

这些数据**已经在 `Photo` 对象里**（`captureTimeMs` / `latitude` / `longitude` / `displayName`），只是没展示。

## 2. 核心决策：单击该做什么

三种模型，必须三选一。

### 模型A（现状）单击 = 选中 · 双击 = 放大

- 好处：选中零门槛，批量操作快
- 代价：缺陷① 的三个后果全都存在
- 适用：如果用户**绝大多数时候都在做多选批量整理**，选中确实该占单击

### 模型B（建议）单击 = 看大图 · 长按 = 进入多选

- 单击**零延迟**打开全屏查看器，没有任何时序猜测
- 长按进入多选模式；**进入后点按即切换选中**（此时不再有冲突，与大图查看分离）
- 与系统相册、微信、Google Photos 一致，用户不需要学习
- 理由：核对照片时「**点开看一眼**」是出现频率最高的动作（每张都要看），而「批量移动」是低频的整理动作（一批做完就走）。**最高频的动作应该占用最轻的那一下。**

### 模型C 单击 = 选中 · 放大按钮

- 零冲突、最省事
- 但每张照片多一个按钮，3 列网格里会拥挤
- 且**拿不到「全屏 + 左右滑动连看」的核对体验**——那正是核对场景的刚需

### 建议

**选模型B。** 核心理由：这个弹窗的首要任务是**核对**（判断照片归属），不是**整理**。核对的单位是"逐张看"，整理的单位是"批量选"。让单击服务核对、长按服务整理，两个动作各归其位。

> 若你的实际使用中**整理远多于核对**，那就选模型A，我改成"选中零延迟 + 放大改用长按"即可（同样消除冲突，只是把高频让给选中）。

## 3. 交互规格（按模型B撰写）

### 3.1 事件弹窗 · 网格

#### 稿件1：未选中态

![未选中](../../_shots/design-sheet-1-idle.png)

| 区域 | 规格 |
|---|---|
| 标题 | 事件名 · N 张；右上「关闭」 |
| 副标题 | 时间区间 · 桩号（**新增**，从事件带出，与照片信息对照） |
| 操作栏 | **未选中时整行隐藏**，不占版面（现状是常显但按钮置灰） |
| 网格 | 3 列；间距 8dp；内容区滚动 |
| 台账角标 | 左下角圆形「1」主色 /「2」琥珀 |
| 底部提示 | 「点按照片查看大图 · 长按进入多选」 |

#### 稿件2：选中态

![已选中](../../_shots/design-sheet-2-selected.png)

| 变化 | 规格 |
|---|---|
| 标题 | 变为「已选 N 张」 |
| 右侧 | 「取消选择」 |
| 操作栏 | **出现**：移动到… / 移出事件 / 设为台账 |
| 单元格 | 3dp 主色边框 + 35% 黑遮罩 + 右上对勾（沿用现状） |

**「移出事件」文案改动**：现状叫「移除」，含义不明（移除到哪？删掉？）。改为「**移出事件**」，并在确认框里写明"回到未匹配池，不删源文件"。

### 3.2 全屏查看器

#### 稿件3：查看器

![查看器](../../_shots/design-sheet-3-viewer.png)

| 区域 | 规格 |
|---|---|
| 顶部工具条 | 关闭 ✕ ｜ 事件名 + `当前/总数 · 拍摄时间 · 桩号` ｜ 设为台账 |
| 主图区 | 双指缩放；双击放大/还原；缩放后单指拖动平移 |
| **左右滑动** | **切换上一张 / 下一张**（核对的核心，现状缺失） |
| 下拉关闭 | 下滑手势退出（大图查看的通用约定） |
| 底部胶片条 | 缩略图横向滚动，当前项主色描边，点击直达 |
| 信息（可选） | 时间 / GPS / 文件名；GPS 与事件群组不一致时给提示 |

**为什么胶片条必要**：核对 7 张照片，若只能左右滑，用户不知道还有几张、当前在哪。胶片条把"全部内容 + 当前位置"一屏给出。

### 3.3 信息辅助（新增，解决缺陷③）

网格单元格在**未选中**时可以叠加极小的信息，帮助判断，不点开也能筛掉明显不对的：

| 信息 | 形式 | 理由 |
|---|---|---|
| 拍摄时间 | 右下角 `09:14` 小字 | 与事件时间区间对照，一眼看出是否落窗 |
| GPS 距离 | 与事件群组中心距离超出阈值时，角标 `⚠远` | 分类引擎已算出 `GPS_FAR` 之类提示，直接复用 |

> 这一条是**可选**的。叠字会让网格变密，若你觉得 3 列格子小，可以只在"异常"时叠角标，正常照片保持干净。

## 4. 完整手势与状态表

| 手势 / 动作 | 网格（浏览模式） | 网格（多选模式） | 全屏查看器 |
|---|---|---|---|
| 单击 | 打开全屏查看器 | 切换该张选中 | 隐藏/显示工具条 |
| 长按 | **进入多选模式并选中该张** | 无 | 无 |
| 双击 | 无（避免与单击冲突） | 无 | 放大 / 还原 |
| 左右滑 | 无 | 无 | 上一张 / 下一张 |
| 下拉 | 无 | 无 | 关闭查看器 |
| 双指捏合 | 无 | 无 | 缩放 |
| 返回键 | 关闭弹窗 | 先退出多选模式 | 关闭查看器（回网格） |

**状态机**：

```
弹窗打开
  └─ 浏览模式（默认）
       ├─ 单击照片 → 全屏查看器 ──返回──> 浏览模式
       └─ 长按照片 → 多选模式（该张已选）
            ├─ 单击其他照片 → 切换选中
            ├─ 操作栏动作（移动/移出/设台账）
            └─ 「取消选择」或返回键 → 浏览模式
```

## 5. 边界情况

| 场景 | 处理 |
|---|---|
| 事件 0 张照片 | 显示「该事件暂无照片」+ 引导去未匹配池 |
| 1 张照片 | 胶片条隐藏（无意义）；左右滑无效但不报错 |
| 全部选中 | 「取消选择」可用；不提供"全选"（核对场景不需要，且误触成本高） |
| 移动目标弹窗 | 沿用现状（带搜索），不变 |
| 移除确认 | 文案改为「移出事件（回到未匹配池，不删源文件）」 |
| 台账标记 | 「设为台账」仅在**恰好选中 1 张**时可用，否则提示"请先选择一张" |
| 正在导出 | 只读：禁用移动/移出/标记，避免导出中途改动分类 |
| 照片文件已不存在 | 单元格显示占位「图片丢失」，不崩 |

## 8. 附：为什么不用 `HorizontalPager` 之外的方案

左右滑动切换实现上有两条路：
- **`HorizontalPager`（Compose Foundation）**：自带预加载与手势，但每页独立缩放需要额外状态管理
- 自绘 + `draggable`：控制力强，但要自己处理边缘回弹

建议用 `HorizontalPager`，缩放状态提升到 pager 层统一管理，避免"滑到下一张还保持着上一张的缩放"这类 bug。
